# 후보 데이터 추가 — 2026-09-19

사용자는 20GB 제한을 해제했다. 현재 단계는 **원본 수집**이며 새 분할 확정·학습은 아직 하지 않는다. 이후 기존 구조의 학습 적합성을 검사하고, 문제를 수정·검증한 뒤 A100 약 16시간 실행으로 이어간다. 기존 7,144개와 제출 산출물은 보존한다.

## 실제 다운로드 목록

`zenodo_plan.json`과 `haim_plan.json`은 원본 URL·정확한 바이트·공식 체크섬·라이선스·원래 split을 고정한 목록이다. 합계 **88,079,995,421 bytes (88.08 GB)**이며 완료량이 아니다.

- VocalSet 1.2 원본 zip. 가수/기법/모음별 중복 정리가 있으므로 압축 내 파일 수를 고유 오디오 수로 세지 않는다.
- CtrSVDD train/dev zip과 프로토콜. 원천 이용조건 때문에 빠진 real 음성이 있어 프로토콜 수와 실제 오디오 수를 반드시 대조한다.
- ASVspoof 5 train 5개 tar, dev 3개 tar, 프로토콜 및 조건 문서. eval 오디오는 이번 다운로드에 넣지 않았다.
- PartialSpoof train/dev, 파일 프로토콜·구간 라벨·VAD·README. eval 오디오는 이번 다운로드에 넣지 않았다. 구간 라벨 archive를 확보해도 pickle을 실행하지 않는다.
- HAIM B1, C1, C2, Lyria 각 500개, 총 2,000개 오디오와 각각의 JSON sidecar. revision `371be01815b65274762d6d0a33e2cb70e24b9baa`, 경로의 SHA-256 순위로 선별했으며 현재 검증된 자료의 새 70/15/15 잠정 분할을 별도로 만들었다. LFS SHA-256 또는 Git blob SHA-1으로 원본을 확인한다.

MUSDB·CodecFake·MLAAD까지 전체를 받는 목록은 아니다. 우선순위로 제시했던 가창·음성·부분 조작·음악 혼합 후보를 먼저 추가한다. 로컬 파일시스템 고갈을 막는 30GiB 여유 공간은 수집 용량 상한과 별개다.

원본 위치: `_workspace/candidate_acquisition_20260919/`. `.part`는 미완료 전송이며 확보량에 포함하지 않는다. `receipts.jsonl`은 첫 Zenodo 실행 기록, `*_receipts.jsonl`은 이후 실행 기록이다. 공개 원본과 byte/hash가 일치해야 최종 파일로 승격된다. 같은 크기의 손상 파일·출력 경로 이탈을 거부하는 검사를 실행했다. 기존 원본을 덮어쓰지 않으며 중단된 전송은 이어받는다.

## 수집 중 확인한 문제

1. **HAIM B7~B9 조건 불일치:** 실제 `original_source_filename`과 곡명에 SONICS real ID 및 상업 발매곡이 나타난다. 상세 설명의 일반적인 CC 원천 문구만으로 개별 이용조건을 확정할 수 없어 오디오 수집을 보류했다. B6도 기존 보류를 유지한다. B1·C1·C2는 MTG-Jamendo 원천 연결과 개별 조건을 다음 검사에서 대조한다.
2. **PartialSpoof를 전부 fake로 두면 틀린다.** 실제 train 프로토콜은 real 2,580 / fake 22,800, dev는 real 2,548 / fake 22,296이다. Claude Opus 5 검토 초안의 일괄 fake 제안은 채택하지 않는다. 구간 라벨 `0=spoof, 1=bona fide`도 우리 코드의 fake=1과 반대다.
3. **원본 프로토콜은 불균형하다.** ASVspoof5 train real 18,797 / fake 163,560, dev real 31,334 / fake 109,616이다. CtrSVDD train real 12,169 / fake 72,235, dev real 6,547 / fake 37,078이다. 이 수치는 메타데이터 행 수이며 다운로드된 오디오 수가 아니다. 원본 전체를 그대로 합쳐 학습시키면 기존의 전체 1:1 목표를 잃는다.
4. **기존 로더의 단일 route:** `full_bank_train.py:170` 이후 학습 대상을 music/voice 중 하나로만 분리하고, `full_bank_features.py:58` 이후 하나의 route 라벨을 요구한다. 혼합곡의 보컬 정답이 생겨도 그대로 넣으면 두 head에 필요한 감독 신호가 전달되지 않는다. 구조를 유지하면서 데이터 선택·known-label mask·손실 연결을 수정하고 실제 gradient로 검증해야 한다.
5. **다운로더 수정:** HF의 작은 JSON은 원본보다 HTTP redirect 응답이 커서 정확한 파일 크기를 curl 전송 상한으로 쓰면 실패했다. redirect용 최소 허용량만 늘리고, 최종 원본은 여전히 정확한 크기와 원격 checksum으로 검증한다. 실제 실패했던 222-byte JSON으로 정상 다운로드와 Git checksum 확인까지 재실행했다.

## 검사와 개선 순서

원본 hash 검증 → archive와 실제 오디오/protocol join → 전체 디코딩·무음·클리핑·시간축·중복 검사 → 원본 발화/화자/가수/곡/파생물 연결 그룹 구성 → 역사적 노출 표시 → 성분별 진위·존재 라벨과 별도 known mask 확인 → 그룹 분할 및 길이·출처 가중치 검사 → 실제 로더/손실/gradient 연결 검사 → 학습·제출 전처리와 예측 일치 검사 순서로 진행한다.

현재 `candidate_data_catalog.py`는 체크섬 검증이 끝난 archive만 색인하고 archive당 최대 3개 오디오를 끝까지 디코딩한다. 이것은 **수집 확인**이며 전체 품질 검사나 학습 승인 완료가 아니다. 학습 편입 행 수는 검사 전까지 0으로 유지한다. 혼합곡은 존재 라벨과 진위 라벨의 미상 여부를 분리하며, 부재 성분의 진위 손실만 마스크한다. 부분 조작에는 같은 편집 조건의 real 대조를 구성한다.

## A100 / 약 16시간 조건

CLI로 확인한 사용 가능 자원은 `resourcespec-a100x1`, A100 SXM 80GB 1대다. 기존 `wsp-9683432r72m7`는 현재 H100 프로필의 stopped/standby이며 **아직 A100으로 전환하거나 GPU를 시작하지 않았다.** A100과 현재 H100은 리전·스토리지 프로필이 다르므로 같은 workspace 전환과 volume 접근 가능성을 배포 전에 확인해야 한다. 새 workspace는 만들지 않는다.

이전 H100 기록에서는 7,144개 특징 추출에 10,574.16초(약 2시간 56분)가 걸렸다. MERT batch 256의 해당 벤치마크 peak는 26,929,689,088 bytes였다. 이것은 A100 실행 측정치도, 새 데이터의 시간 보장도 아니다. A100 CPU/RAM도 H100 프로필과 다르며 긴 음악·전체 창 수·DF-Arena 단일 파형 경로가 시간을 늘릴 수 있다.

학습 파일을 확정한 뒤 유형·길이 구간별로 실제 전체 파이프라인 처리 시간을 재고, 전체 오디오 길이와 창 수로 예상 시간을 합산한다. VRAM은 모델을 함께 올린 상태에서 peak를 측정하고 여유를 남기는 batch를 고른다. 16시간에는 준비·특징 추출·모든 seed 학습·검증·체크포인트·결과 내보내기를 포함한다. 예상이 넘으면 학습을 시작하지 않고 캐시 재사용·중복 처리 제거·길이별 batching 등부터 개선한다. 시간에 맞추려고 파일을 몰래 누락하거나 검증을 생략하지 않는다.

공개 출처는 `metadata/`의 원본 레코드·README·라이선스와 각 다운로드 plan에 남겼다. Claude 앱 Opus 5의 보조 검토는 `claude_preflight_review.txt`에 보관했다. 외부 AI의 제안은 검사 항목을 보조할 뿐 실제 데이터·코드 검증이나 사용자의 추가 승인 요구를 대신하지 않는다.

## 추가 수집분 재구성 — 2026-09-19 갱신

사용자가 총 개수 제한을 없애고 train/val/test 70/15/15를 선택했다. 실제 새 분할과 검사 결과는 `../reconstructed_bank_20260919/README.md`와 CSV에 있다. 현재 스냅샷은 13,186개이고 real/fake 1:1을 유지한다. 새 수집 오디오 785개가 실제 선별 목록에 포함됐다. 아직 다운로드·부모 연결·부분 편집 대조 검사가 남은 후보는 학습에 넣지 않았다. 수집 색인의 `training_admitted_rows=0`은 색인 도구가 학습 승인을 하지 않는다는 뜻이며, 새 분할의 후보 선별 수량과 구별한다. 새 분할도 `training_ready=false`이고 GPU는 정지 상태다.

최신 HAIM 2,000개 전체를 반영한 스냅샷은 `../reconstructed_bank_20260919_haim_complete/README.md`다. 앞선 수량·노출·진단은 각 작성 시점의 기록이며, 최신 결과는 이 스냅샷을 따른다.
