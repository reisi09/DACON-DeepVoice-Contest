# 기존 G0–G4 그래프의 성능 변화 진단

## 범위와 계산 방법

이 문서는 `results/v2_forensics.json`을 다시 읽어 기존 225개 검증 파일에서 G0–G4가 바꾼 점과 결과를 정리한 기록이다. 여기서 `dev` 160개와 기존 `holdout` 65개는 모두 새 V2의 개발 자료로 취급한다. 특히 기존 holdout은 이미 그래프 설계와 비교에 사용됐으므로 새 데이터에서의 일반화 성능이나 리더보드 성능을 뜻하지 않는다. 새 `test_generator`와 `test_source`는 이 진단 시점에 열지 않았다.

EER은 점수를 보간하지 않았다. 점수 동률을 하나의 ROC 점으로 묶은 뒤 `|FPR-FNR|`가 가장 작은 첫 점을 골랐다. 표의 `FP,FN`은 바로 그 점에서의 오탐과 누락 수이며, AUC는 같은 점수 전체의 순위 품질이다. 따라서 EER이 바뀌고 AUC가 좋아질 수 있으며, 반대도 가능하다.

## 그래프가 실제로 바꾼 계산

| 그래프 | 파일 단위 계산에서 바뀐 부분 | 학습 여부 |
| --- | --- | --- |
| G0 | 음성·음악 fake 최대값에 각 존재 확률 최대값을 곱하고 둘 중 큰 값을 `FILE_FAKE`로 사용 | 없음 |
| G1 | 음성·음악 fake의 최대 두 window 평균을 사용하고, 존재 확률은 G0와 같게 유지 | 없음 |
| G2 | window별 `voice_presence × voice_fake`와 `music_presence × music_fake`를 noisy-OR로 합쳐 파일 fake를 계산. 개별 음성·음악 fake와 존재 확률은 G0와 같음 | 없음 |
| G3 | 원본 audio fake 점수와 `0.75 × component_fake 최대값 + 0.25 × raw_fake`를 함께 사용. 파일 fake는 raw와 존재 확률을 반영한 두 component 후보의 최댓값 | 없음 |
| G4 | G0를 시작점으로 하되, dev에서 적합한 logistic head가 있으면 11개 파일 내부 특징으로 `FILE_FAKE`, `VOICE_FAKE`, `MUSIC_FAKE`를 교체. 특징에는 각 점수의 최대·평균, 존재 확률 최대, raw/component 차이, window 수가 포함 | dev만 사용 |

모든 그래프는 한 파일의 window와 고정된 파라미터만 사용한다. 그래프 사이의 차이는 위 계산식에서 직접 확인한 사실이다. 반면 어떤 검출기가 특정 생성기·장르·변환 때문에 변했는지는 이 표만으로 결정할 수 없다.

## 기존 데이터가 제공하는 증거의 범위

기존 dev에는 원자 source group 43개가 있지만 mixture의 구성원을 연결하면 독립적인 lineage component는 31개다. 기존 holdout도 원자 group 21개가 아니라 연결 component 17개다. clip을 독립 표본으로 간주하면 불확실성이 작게 보일 수 있으므로, V2 선택에서는 이런 연결 component를 bootstrap 단위로 쓴다.

음성 존재 라벨도 완전하지 않다. dev에서 `VOICE_PRESENT`가 알려진 140개는 모두 1이고 20개는 미상이다. 기존 holdout도 알려진 52개가 모두 1이고 13개는 미상이다. 이 때문에 두 구간 모두 음성 존재 AUC는 양·음성 클래스가 함께 없어 계산할 수 없다. 음성 fake EER도 dev 128개, holdout 48개의 알려진·음성 존재 파일에서만 계산했다. 반대로 음악 존재 라벨은 두 구간에서 완전하며, 음악 fake EER은 실제 음악이 있는 dev 68개와 holdout 29개로 계산했다.

## dev에서 관찰한 변화

아래 값은 `EER / AUC (FP,FN)` 순서다. G4는 dev에서 계수를 적합했으므로 이 표는 G4의 일반화 증거가 아니라 학습에 쓰인 구간에서의 적합 결과다.

| 그래프 | 파일 fake, n=160 | 음성 fake, n=128 | 음악 fake, n=68 |
| --- | --- | --- | --- |
| G0 | 0.187500 / 0.918457 (12,18) | 0.031527 / 0.986700 (2,2) | 0.294737 / 0.700000 (9,11) |
| G1 | 0.187500 / 0.919108 (12,18) | 0.054433 / 0.986207 (3,4) | 0.307895 / 0.687719 (9,12) |
| G2 | 0.156250 / 0.929199 (10,15) | 0.031527 / 0.986700 (2,2) | 0.294737 / 0.700000 (9,11) |
| G3 | 0.169271 / 0.928711 (11,16) | 0.054433 / 0.985468 (3,4) | 0.367544 / 0.689474 (11,14) |
| G4 | 0.143229 / 0.938477 (9,14) | 0.038670 / 0.986453 (2,3) | 0.337719 / 0.770175 (10,13) |

G2의 파일 fake 개선과 G4의 파일 fake 개선은 dev에서 측정됐다. 그러나 G4는 이 구간의 레이블로 head를 적합했으므로, 같은 표의 개선을 새 출처 성능으로 해석하면 안 된다. G1과 G3는 파일 fake AUC를 조금 높였지만 음성·음악의 이산 EER은 악화했다. 이는 파일 기준 계산식이 component 기준 ROC 교차점을 동시에 개선하지 못했다는 관찰이다.

## 기존 holdout에서 관찰한 변화

이 구간도 새 테스트가 아니라, 기존 파이프라인이 약화된 양상을 찾기 위한 후향 진단 구간이다.

| 그래프 | 파일 fake, n=65 | 음성 fake, n=48 | 음악 fake, n=29 |
| --- | --- | --- | --- |
| G0 | 0.123476 / 0.945122 (3,5) | 0.041958 / 0.980769 (1,1) | 0.307895 / 0.721053 (3,6) |
| G1 | 0.123476 / 0.956301 (3,5) | 0.083916 / 0.984266 (2,2) | 0.307895 / 0.763158 (3,6) |
| G2 | 0.123476 / 0.924797 (3,5) | 0.041958 / 0.980769 (1,1) | 0.307895 / 0.721053 (3,6) |
| G3 | 0.156504 / 0.954268 (4,6) | 0.041958 / 0.982517 (1,1) | 0.384211 / 0.721053 (4,7) |
| G4 | 0.156504 / 0.935976 (4,6) | 0.041958 / 0.991259 (1,1) | 0.307895 / 0.726316 (3,6) |

G1은 파일·음악 AUC를 각각 0.011179, 0.042105 높였고, 파일·음악 EER의 ROC 교차점은 G0와 같다. 다만 음성 fake는 AUC가 0.980769에서 0.984266으로 높아졌는데도 EER은 0.041958에서 0.083916으로 바뀌었다. 선택된 ROC 점의 FP,FN이 `(1,1)`에서 `(2,2)`가 된 결과다. 따라서 G1을 “순위가 전반적으로 나빠졌다”고 부를 근거는 없고, 이 표본에서 EER이 고른 작동점이 불리하게 이동했다고만 말할 수 있다.

G2는 component 점수와 존재 확률을 결합하는 파일 계산만 바꿨다. holdout에서 파일 EER 교차점은 G0와 같지만 AUC는 0.945122에서 0.924797로 낮아졌다. 음성·음악 component 출력은 G0와 동일하므로 두 component 지표도 동일하다. 이 결과는 G2의 파일 정렬 변화가 dev의 개선을 holdout으로 옮기지 못했다는 증거다.

G3는 파일 fake에서 EER이 0.123476에서 0.156504로, FP,FN이 `(3,5)`에서 `(4,6)`으로 늘었다. 음악 fake도 EER이 0.307895에서 0.384211로, FP,FN이 `(3,6)`에서 `(4,7)`으로 늘었다. 그런데 음악 AUC는 두 경우 모두 0.721053이다. raw 점수를 섞는 방식이 모든 음악 positive/negative 순위를 무너뜨렸다는 뜻은 아니며, 같은 AUC 안에서 이산 EER 교차점이 달라진 것이다. G3의 raw 혼합이 특정 유형에 “오염”을 일으켰다는 해석은 현재 자료만으로는 가설일 뿐이다.

G4는 dev 파일 EER이 0.143229까지 낮아졌지만 기존 holdout 파일 EER은 0.156504로 G0보다 높아졌고, AUC도 0.945122에서 0.935976으로 낮아졌다. G4 head가 dev 레이블에 적합됐다는 사실과 이 dev-to-holdout 차이는 측정됐다. 다만 17개 연결 component의 기존 holdout만으로는 이것이 계수 과적합, 출처 차이, mixture 비율, 변환 효과 중 무엇 때문인지 분리할 수 없다.

## positive–negative 쌍의 순위 변화

각 셀은 `변경된 쌍 수 / G0에서 positive가 앞섰다가 candidate에서 뒤진 쌍 수`다. 동점으로 바뀐 경우는 이 카운트에 넣지 않았다. 파일·음성·음악의 비교 가능한 positive–negative 쌍 수는 각각 984, 572, 190개다.

| 그래프 | 파일 fake | 음성 fake | 음악 fake |
| --- | --- | --- | --- |
| G1 | 15 / 2 | 4 / 1 | 12 / 2 |
| G2 | 28 / 24 | 0 / 0 | 0 / 0 |
| G3 | 37 / 14 | 1 / 0 | 20 / 10 |
| G4 | 57 / 33 | 6 / 0 | 27 / 13 |

쌍 카운트는 왜 EER과 AUC를 함께 봐야 하는지 보완한다. 예를 들어 G1 음성에서는 4개 쌍의 순서가 바뀌고 그중 1개가 positive-to-negative로 바뀌었지만 AUC는 상승했다. G3 음악에서는 20개 쌍이 바뀌고 10개가 adverse 방향이었으며 AUC는 동일했다. G4 파일은 57개 쌍이 바뀌고 33개가 adverse 방향이었고, AUC도 감소했다. 이 값들은 순위 변화의 양을 보여 주지만, 원인을 출처·생성기 하나로 귀속하지는 않는다.

## 현재 진단에서 확정할 수 있는 것과 남는 한계

확정할 수 있는 사실은 G1·G3·G4가 G0와 다른 ROC 순위와 EER 작동점을 만들었고, G1 음성 및 G3 음악처럼 AUC와 EER의 방향이 갈린 경우가 있다는 점이다. G4의 dev 개선이 기존 holdout으로 그대로 이어지지 않았다는 점도 확인됐다. 이를 근거로 기존 G0를 유지하고, V2 후보는 기존 holdout이 아닌 source-disjoint `dev_select`에서만 고른다.

반면 이 진단은 DACON 리더보드 점수, 새 생성기 일반화, 새 출처 일반화, L4 시간 제한 충족을 보여 주지 않는다. 음성이 없다고 확인된 파일이 없어 음성 존재 AUC도 계산하지 못했다. 새 source-disjoint 테스트는 checkpoint를 잠근 뒤 한 번만 평가해야 하므로, 이 문서에서 그 결과를 예측하거나 그에 맞춰 그래프를 조정하지 않는다.
