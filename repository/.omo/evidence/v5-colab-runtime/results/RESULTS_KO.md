## 자체 검증 성능

EER은 낮을수록, AUC는 높을수록 좋다.

| 파이프라인 | FILE EER | VOICE EER | MUSIC EER | 음성 존재 AUC | 음악 존재 AUC |
|---|---:|---:|---:|---:|---:|
| B0 베이스라인 | 0.378175 | 0.150000 | 0.542222 | 0.997917 | 0.985132 |
| B1 전체 미세조정 | **0.321825** | 0.170833 | **0.368333** | **0.998333** | **0.985855** |
| B2 전체 미세조정 + 증강 | 0.378175 | **0.150000** | 0.457778 | 0.969583 | 0.593553 |
| B3 시간 순서 결합 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |
| B4 공동 상태 결합 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |

B1은 B0보다 FILE EER이 0.056349, MUSIC EER이 0.173889 낮았다. 반면 VOICE EER은 0.020833 높아졌다. 모든 판별 성능이 함께 좋아진 결과는 아니다.

B2는 음악 판별 EER이 B0보다 낮았지만, 음악 존재 여부 AUC가 크게 떨어졌다. 파일 판별 EER은 B0와 같았다. 증강 자체가 항상 해롭다는 결론은 내릴 수 없다. 증강 연산으로 에포크 시간이 늘었고, 모델별 실제 학습량과 검증된 에포크가 달랐기 때문이다.

검증 230개에는 동일한 splice 음원이 중복되어 있어 실제 고유 음원은 210개다. 동일 음원들의 예측 차이는 B0·B1·B2 모두 0이었다. 중복을 한 번씩만 계산하면 FILE EER은 B0 **0.337981**, B1 **0.310096**, B2 **0.375962**다. B1이 더 좋다는 순서는 유지되지만 개선 폭은 작아진다. 모델 선택에는 기존 230개 기준을 유지했고, 210개 결과는 민감도 분석으로만 사용했다.

VOICE EER은 관련 라벨을 아는 100개, 음성 존재 AUC는 140개에서 계산했다. 알려지지 않은 라벨은 제외했다. 따라서 공식 종합 점수는 계산하지 않았으며 JSON의 `known_subset_proxy`도 리더보드 점수로 해석하면 안 된다.

## 이번 실행의 추론 시간

검증 음원 230개 전체를 처리한 전문가별 추론 기록이다. 가중치 로딩·설치·학습 시간은 포함하지 않는다.

| 파이프라인 | 음성 | 음악 | 존재 여부 | 세 추론 작업 합계 |
|---|---:|---:|---:|---:|
| B1 | 54.76초 | 8.98초 | 7.97초 | 71.71초 |
| B2 | 55.16초 | 8.96초 | 8.03초 | 72.15초 |

B1·B2는 원음을 바로 사용하고 음악 탐지에 SONICS를 사용하므로, 음원을 분리하는 B0와 처리 과정이 다르다. 짧은 시간만으로 누락이나 오류를 판단할 수는 없다. 이번 결과는 CSV의 230개 ID가 검증 목록과 정확히 일치하는지 확인했다. B0는 210개 예측을 재사용했으므로 이번 실행의 B0 소요 시간과 위 숫자를 직접 비교하면 안 된다. 이 기록은 Colab A100에서 측정했으며 DACON 채점 서버 실행 시간은 아니다.

학습 중 체크포인트 검증은 autocast를 끄고 수행했으며 최종 파일별 예측은 BF16 autocast를 사용했다. 학습 곡선과 최종 표의 값이 조금 다를 수 있다. 위 성능 표는 저장된 최종 CSV를 다시 계산한 결과다.

## 파이프라인과 실패 원인

- **B0:** 공식 G0. 음원 분리와 기존 사전학습 탐지기, 존재 여부 점수를 조합한다. 210개 예측은 이전 실행에서 가져왔으므로 이번 실행 시간만으로 전체 B0 추론 속도를 비교할 수 없다.
- **B1:** 원음 구간 → DF-Arena 1B 음성 탐지기 / SONICS 음악 탐지기 / PANNs 기반 2개 존재 여부 헤드 전체 미세조정 → 파일 전체 구간의 최댓값 → 존재 여부로 가중한 파일 판별.
- **B2:** B1 구조에 채널 증강을 추가한다. 실제 에포크 수가 달라 B1과의 차이는 증강만을 분리한 효과가 아니다.
- **B3 계획:** B2 가중치로 원음·분리 음원의 구간별 임베딩과 판별 차이를 추출 → 시간 순서를 유지한 Transformer → 독립 판별 헤드.
- **B4 계획:** 같은 입력과 시간 순서 모델 → 음성/음악의 부재·진짜·가짜 조합인 9개 상태를 공동 예측 → 최종 확률 산출.

실행 로그의 마지막 전처리 진행 표시는 `SEPARATE train 1451/1736`이다. 이후 `Full raw/stem preparation exceeded its stage budget` 오류가 발생했다. 진행 로그는 50개마다 출력되므로 정확한 최종 전처리 완료 개수는 이 로그만으로 알 수 없다.

전체 2시간 한도가 소진된 것은 아니다. 전처리에 남은 시간의 35%만 허용한 내부 배분이 먼저 한계에 도달했다. 런타임 해제 요청은 최초 할당 요청으로부터 **5,365.78초(약 89.43분)** 뒤에 기록됐다. 이 값은 순수 학습 시간이 아니라 설치·준비·실험을 포함한 경과 시간이다.

복구 코드와 캐시 재사용 절차를 준비했지만 Aside 제어에서 `The user changed '/Applications/Aside.app'` 오류가 반복되어 복구 명령을 적용하지 못했다. `supervise_temporal.py`와 `v5_resume_temporal.py`는 준비된 코드이며 실행 성공 기록이 아니다. 해제 요청 이후 2026-09-14 00:41 KST에 Colab의 **활성 세션 없음** 화면을 확인했다. `gpu_session_verification.txt`에 확인 기록을 남겼다.

## 수정한 재실행 코드

1. 전처리·특징 추출은 전체 종료 시각에서 300초를 뺀 공통 제한을 사용한다. 작업별 35%/48%/84% 제한을 제거했으며 전체 실행 한도를 늘리지 않았다. 이 변경만으로 B3·B4의 학습 완료가 보장되지는 않는다.
2. 다음 학습·검증 주기가 남은 시간에 들어가지 않으면, 현재 완료한 에포크를 검증하도록 바꿨다. 기존 B2 존재 여부 모델은 4에포크 중 1에포크만 검증되어 선택 후보가 제한됐다. 수정 전 기록의 성능을 수정 후 결과로 바꾸지 않았다.
3. 파이프라인 상태에 실제 `budget_stop`을 반영한다. 초기화만 된 시간 순서 모델이나 미실행 모델을 평가 완료로 표시하지 않는다.
4. 원음/분리 음원의 샘플링 주파수·길이·시간축을 확인한 뒤 완전한 캐시만 재사용하는 복구 실행 파일을 추가했다.

실행본은 `executed.ipynb`이며 SHA-256은 `4993fb5b14b65d65f25e4ac968202a2b5f8bdd51d6fac48aaf24d40da876d457`이다. 현재 실행 셀의 마지막 출력이 일부 빠질 수 있다는 캡처 기록도 함께 보존했다. 실행 도중 적용한 학습 모드 패치는 `runtime_mode_patch.json`에 남겼고, 기록된 소스 해시와 일치하는 20개 파일을 `runtime_source_snapshot.zip`에 보관했다. 수정한 재실행 노트북은 이 실행본과 별개다.
