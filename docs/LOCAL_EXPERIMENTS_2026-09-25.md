# Mac 로컬 실험 결과 — 2026-09-25

기존 특징 캐시로 가능한 비교 학습·수치 검증을 실행했다. 현재 진단 자료에서 새 구조를 채택할 근거가 없어 DataV4 보존 모델을 유지한다. 새 제출물은 만들지 않았고 클라우드 자원을 기동하지 않았다. 아래 결과는 리더보드 ADS·CPS의 측정값이나 예측값이 아니다.

## 실행 범위와 데이터 한계

- Mac M5 Pro, 24 GiB RAM, PyTorch 2.7.1에서 실행했다. 작은 헤드의 실제 학습 step을 CPU·MPS에서 비교한 뒤 더 빠른 CPU로 학습했다.
- 캐시 5,952행의 내용 해시·행 정체성·추출기 출처를 검사했다. train 5,196, selection 421, calibration 335행이다. 현재 역할 사이에 같은 `component_id`나 음원 SHA-256이 겹치지 않는다. 이 확인이 모든 숨은 원천 관계의 부재를 증명하지는 않는다.
- **5,952개 모두 보존 모델의 과거 train/val에 있던 ID다.** 따라서 selection·calibration이라는 이름이 독립적인 평가를 뜻하지 않는다. 원천 일반화나 공식 점수 개선을 판정할 수 없다.
- 추가 편입 1,477개(LibriSpeech 449, MusicArena 882, MLAAD 146)의 현 캐시 포함 수는 **0개**다. 이번 재가중 실험은 기존 데이터의 비중만 바꿨으며 추가 데이터 학습이 아니다.
- 실제 헤드 학습 대상은 음악 373행, 음성 5,001행이다. 음악 calibration은 43행, 음성은 알려진 라벨 308행이다. 일부 라벨이 없어 공식 합산 점수는 계산하지 않았다.

## 실제 학습 비교

각 후보를 seed 41·42·43, 20 epoch로 학습했다. 마지막 epoch를 고정 사용했고 검증 결과로 epoch를 고르지 않았다. 음악 후보끼리는 각 60 step, 음성 후보끼리는 각 800 step이다. 특징 추출기·presence·CDF FILE 결합기는 고정했다. residual 후보는 기준 분류기도 동결했고 선형 대조군은 해당 선형 헤드를 갱신했다.

| 후보 | 학습 파라미터 | selection 목표 EER | calibration 목표 EER | calibration FILE EER |
|---|---:|---:|---:|---:|
| 기존 음악 기준 | 추가 학습 없음 | 11.44% | **9.31%** | 5.60% |
| 음악 residual k=1 | 80,705 | 5.72% | 13.96% | 4.48% |
| 음악 residual k=3 | 105,281 | 5.72% | 13.96% | 5.78% |
| 기존 음성 기준 | 추가 학습 없음 | 3.76% | **2.36%** | 5.60% |
| 음성 선형 재학습 | 2,562 | 4.07% | 4.13% | 5.97% |
| 음성 선형 재가중 | 2,562 | 5.02% | 5.52% | 5.97% |
| 음성 residual MLP | 166,657 | 4.07% | 4.13% | 5.78% |

목표 EER은 음악 후보에서는 Music EER, 음성 후보에서는 Voice EER이다. 다른 경로는 그대로 두었다. 음악 k=1의 FILE 개선만으로 채택하지 않는다. 음악 자체의 EER이 악화됐고 표본도 작다. k=3와 k=1의 calibration Music EER 차이에 대한 component 단위 paired bootstrap 95% 구간은 **−4.75~+11.52%p**(400회)다. 시간축 후보의 추가 이득은 확인되지 않았다. 두 후보의 파라미터 수도 달라 순수한 시간 문맥의 인과 효과를 분리한 비교는 아니다. seed별 결과와 나머지 불확실성은 [수치 기록](evidence/local_experiments_20260925/summary.json)에 있다.

15개 학습과 진단·저장·재추론을 포함한 실행은 약 65.1초, 해당 프로세스 최대 RSS는 약 0.97 GiB였다. 대형 인코더 특징 추출 시간은 포함하지 않는다. 작은 배치의 8-step 측정값은 음악 CPU 32.46ms/MPS 119.01ms, 음성 CPU 0.98ms/MPS 45.62ms였다. 별도 충분한 warm-up을 둔 일반 처리량 벤치마크가 아니므로 인코더나 큰 배치까지 이 비율을 적용하지 않는다.

## 구조를 바꾸지 않는 진단

- 기존 음성 max 집계를 LME로 바꾸면 calibration Voice EER 2.36% → 3.74%, top-30%로 바꾸면 3.55%였다. 채택하지 않는다.
- selection에서 적합한 단조 logit 보정은 calibration Voice EER을 유지하면서 FILE EER을 5.60% → 4.48%로 낮췄다. 순위 판별력의 개선은 아니다. 기존 모델에 노출된 자료로 보정했으므로 배포하지 않는다.
- logit에 PANNs singing 점수를 추가한 보정은 calibration Voice EER 3.74%였다. 현재 결과로는 가창 조건 추가의 이득이 없다.
- 보존된 전체 proxy 예측 6,444행을 다시 계산했다. 은닉 test나 새로운 holdout이 아니라 이미 검토한 과거 진단 자료다. bank 6,450행 중 예측이 없는 6행은 만들어 채우지 않았다.

| 기존 전체 proxy의 부분집합 | 행 수 | EER |
|---|---:|---:|
| 음악 없는 음성 | 3,595 | 4.43% |
| 음악과 함께 있는 음성 | 1,544 | 20.60% |
| 음악 판별 대상 | 2,849 | 20.01% |

혼합 음성 안에서도 순위 오류가 남는다. 다만 `voice_with_music`는 검증된 가창 라벨이 아니므로 가창 전체의 성능으로 부르지 않는다. FILE 결합을 저장된 성분 출력에서 복원한 최대 오차는 `1.11e-16`이다. presence와 결합기를 고정하고 알려진 성분 정답만 대입한 진단에서 FILE EER은 기준 10.94%, 음악 정답 대입 4.45%, 음성 정답 대입 6.07%였다. 이는 바꾼 성분의 영향 진단이며 실현 가능한 개선 폭이나 성능 상한의 증명이 아니다.

## 구현·실행 검증

- 실제 캐시와 보존 가중치에서 residual 초기 출력이 기준과 일치했다(`atol=2e-6`, `rtol=1e-6`).
- 실제 optimizer 3회 갱신 후 의도한 모든 학습 파라미터에 유한한 비영 gradient와 값 변화가 있었다. 동결한 기준 헤드는 값이 그대로였고 gradient가 없었다.
- NaN을 넣은 padding이 출력에 영향을 주지 않았고, 단독/묶음 추론도 허용 오차 안에서 일치했다. 불규칙한 마지막 구간 간격을 보존한다.
- CPU·MPS의 실제 갱신 후 예측과 저장 후 복원을 `atol=rtol=2e-4`로 비교했다. 모든 학습 체크포인트의 CPU 예측 재생은 정확히 일치했고 presence 출력도 변하지 않았다.
- 기존 temporal 기본 동작, 누적 gradient, MIL 집계, ROC 동점·라벨 마스크, 캐시 출처 거부와 역할 분리 검증을 함께 통과했다. 기록은 28 passed, 1 deselected, 8 subtests passed다. 이 개수가 모델 품질을 증명하지는 않는다.
- 별도 검토자는 코드와 실행 기록을 읽고 수정이 필요한 결함을 보고하지 않았다. 재학습이나 실제 음원 검증을 대신한 것은 아니다.

## 실제 음원 CPU·MPS 검증

DataV4 제출 패키지의 53개 구성 파일을 보존 영수증과 대조해 별도 경로에 풀었다. 음성·음악·혼합, WAV·FLAC·MP3를 포함한 기존 실제 음원 10개로 추론했다. 네트워크를 OS sandbox에서 막고 가중치는 `weights_only=True`로 읽었다. HTDemucs에는 확인한 클래스·NumPy 구형 scalar 별칭·float64 dtype·Fraction만 명시적으로 허용했다. 기존 로더의 무제한 역직렬화로 돌아가지 않았다.

| 확인 항목 | 실제 결과 |
|---|---|
| CPU 실제 패키지 CLI, 10개 | 기존 저장 결과의 5열 모두 최대 절대 오차 **0** |
| CPU 2개 역순 부분집합 | 전체 묶음과 최대 절대 오차 **0**, 요청한 ID 순서 유지 |
| MPS Engine, 같은 10개 | 오류 없이 완료. CPU 대비 최대 절대 오차 **2.60e-5** |
| MPS에 CPU 재현 기준 `1e-5` 적용 | **미충족**. 실행 가능 확인과 엄격한 수치 동등성을 구분한다. |
| MPS의 실제 장치 | HTDemucs·DF-Arena·MERT 파라미터는 `mps:0`, PANNs는 CPU |

CPU 10개는 프로세스 기준 95.08초, MPS 10개는 23.06초였다. CPU CLI에는 패키지 해시 검사가 포함되고 MPS는 Engine 직접 호출이므로 공정한 속도 배율 비교는 아니다. MPS 파일별 추론 합계는 약 12.74초였고, 파일 완료 시 측정한 최대 Metal driver 할당량은 약 7.85 GiB였다. MPS의 CPU RSS 약 2.41 GiB만을 전체 메모리 사용량으로 보고하지 않는다. 긴 음원·1,477개 전체 추출이나 장시간 메모리 안정성은 검증하지 않았다.

제출 CLI 자체의 장치 선택은 여전히 CPU/CUDA다. 이번 MPS 실행은 별도 진단 harness이며, 실제 제출 패키지의 MPS 지원이나 공식 L4 환경 검증으로 표현하지 않는다. MPS에 CPU fallback 환경변수를 켜지 않았지만 PANNs의 기존 CPU 선택과 라이브러리 내부 CPU 처리가 있을 수 있어 전체 경로를 순수 MPS라고 부르지 않는다.

격리 실행 중 발견한 Python 심볼릭 링크 경로·PANNs 전역 라벨 복사·Numba 캐시 쓰기 문제는 진단 harness에서 처리했다. 실제 Python 설치 경로의 읽기만 허용하고, PANNs 라벨은 원본과 바이트가 같은 기존 파일을 읽어 불필요한 덮어쓰기를 생략했으며, Numba/Matplotlib 캐시는 작업 출력 폴더로 지정했다. 원본 제출 ZIP·기존 QA 결과·음원·가중치를 덮어쓰지 않았다. 관련 실패 기록도 원본 로그와 함께 보존했다.

추가 1,477개 학습, raw+stem·다층 MERT 비교, 독립 holdout 품질 검증은 완료하지 않았다. 이들은 현 캐시에 없는 특징이나 노출을 배제한 평가 자료가 필요하다. 이번 요청에서 바로 실행할 수 있었던 캐시 기반 비교와 로컬 실행 검증의 완료를 이 단계들의 완료로 확대 해석하지 않는다.
